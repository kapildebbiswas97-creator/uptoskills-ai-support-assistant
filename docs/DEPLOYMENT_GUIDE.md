The repository has no `.nvmrc` or `engines` field, so the deployed Node runtime relies on platform defaults. A Vite production build succeeded, but it does not compile or execute the Vercel function. The configured project root, runtime selection, function bundle, environment variables, logs, streaming behavior, and deployed revision were not available for verification. No deployment was performed.

## Phase 9.1 serverless ESM verification (2026-11-15)

Production Vercel logs supplied for this continuation identify the serverless crash as Node ESM failing to resolve extensionless relative imports, first `../server/app` from `api/[...path]`. Relative runtime imports in the transitive API graph now use explicit `.js` specifiers. `npm run build` begins with `scripts/check-serverless-esm-graph.mjs`, which uses esbuild to audit the API-reachable local import graph, emits a Node 26-target ESM bundle, imports it under the installed Node runtime, and runs a Preview-mode local HTTP smoke check. This verifies local output only; Vercel CLI build and actual Preview remain separate release gates.

The Preview smoke test deliberately clears service environment variables in its child process, expects health 503 when MongoDB/PostgreSQL/OIDC/model settings are absent, and verifies protected APIs return 401. Missing Preview configuration no longer aborts serverless app construction before route-level authorization/readiness checks. Production/Preview chat requires authentication even if `ALLOW_ANONYMOUS_CHAT=true`. Core hosted workflows remain unavailable until the variables listed in [ENVIRONMENT_VARIABLES.md](ENVIRONMENT_VARIABLES.md) are configured and live-tested.

1. Configure the Vercel project root to this repository root. Select and pin a Node runtime compatible with the checked-in dependency versions, then verify the serverless function bundle in staging.
2. Populate isolated staging variables and run `npm run env:validate:staging`. Configure the trusted OIDC issuer/audience and explicit provider-role mapping before enabling protected operations.
3. Provision MongoDB Atlas and separate PostgreSQL reader, writer, and migration accounts. Require TLS in provider connection settings. Also set Preview-only `RLS_CONTEXT_KEY_ID` and `RLS_CONTEXT_HMAC_KEY` from the approved secret manager; provision the identical key into the target database with an operator-controlled, parameterized process.
4. Review and apply MongoDB setup and PostgreSQL migrations deliberately, including migration 004. Confirm app roles are not table owners, `BYPASSRLS`, `CREATEROLE`, or members of privileged/key-admin/context-owner roles, then verify signed tenant contexts and rollback/pool cleanup. Do not run production migrations without a verified backup and explicit approval.
5. Configure a malware scanner implementing the documented HTTPS scan contract. Without a configured scanner, ingestion fails closed.
6. Configure one Gemini API key for embeddings and a supported chat provider key for model responses.
7. Configure a shared Redis instance if globally consistent rate limits are required; the process-local fallback does not coordinate serverless instances.
8. Confirm Vercel function duration, worker/thread compatibility, and buffered SSE behavior with a staging deployment, then inspect function logs and health checks.

Production is not ready until real database connectivity, signed RLS and key rotation, issuer claims, SSE, deployed routing, backup settings, and recovery have been verified in isolated staging. This checkout contains migration 004 but no real DB has applied it; deployments must not assume the older migration 003 is hardened.

Persistent HR escalation and meeting request/review routes and views are present in source. Their generated-key local HTTP tests use a test service for API journeys, and meeting Mongo transaction tests use a mock; no real browser OIDC session or live Mongo persistence has been verified. The queue-first meeting implementation still requires D-07 policy approval (especially reviewer/tenant authority) and retention decisions. No calendar provider, notification sender, or external event integration is configured. Production readiness still requires isolated service verification and stakeholder decisions D-05 through D-09.

## Phase 5 staging preview configuration

The Vercel project root must be the directory containing `package.json`, `vercel.json`, `api/`, and `src/` (the supplied `work/source-archive` directory). Set Root Directory to that directory, use the Vite framework preset, install with `npm ci`, build with `npm run build`, and serve `dist`. Keep `api/[...path].ts` as the Node.js serverless entrypoint; the checked-in `vercel.json` sets its maximum duration to 60 seconds and includes `knowledge.yaml` and `docs/**`. Select and test a supported Node.js major explicitly in Vercel settings; this repository has no `engines` field or pinned runtime. The local runtime tested here is Node.js `v24.16.0`; typings are `@types/node` 22.x. Vercel currently documents Node.js 24.x as the default and 22.x as supported. [Node.js versions](https://vercel.com/docs/functions/runtimes/node-js/node-js-versions)

For Preview scope, configure only verified isolated staging values. Set `APP_ENV=staging` or rely on Vercel's `VERCEL_ENV=preview`; either enables staging auth and strict environment validation. Supply `MONGODB_URI`/`MONGODB_DATABASE`, `AUTH_ISSUER`/`AUTH_AUDIENCE` and explicit `AUTH_ROLE_MAPPING`, TLS PostgreSQL `DATABASE_URL` and `DATABASE_INGEST_URL`, embedding and AI provider keys, and scanner endpoint/token. Keep migration credentials out of function scope. Leave anonymous chat unset or false. Choose the Vercel function region near the staging databases after confirming the region and data-residency requirements; no region is specified in this repository.

Vercel documents a 4.5 MB request and response payload ceiling. JSON/base64 increases file size, so document and chat-PDF raw files are capped at 3 MiB and JSON parsing is capped at 4.2 MiB. [Vercel Functions limits](https://vercel.com/docs/functions/limitations). The 60-second function limit aligns with the app's default 55-second chat timeout, but plan/runtime limits can differ; confirm it in Preview. The response uses SSE headers and disables proxy buffering; local HTTP tests verify app headers, cancellation, and timeout behavior, but no Vercel Preview SSE route was exercised.

Vercel project root, settings, environment-variable scopes, serverless bundling, runtime/worker compatibility, payload enforcement, regional placement, and deployed SSE behavior remain unverified because no Vercel project access or staging deployment was available. Do not deploy until a Preview deployment exercises `/api/models`, `/api/chat`, `/api/chat/stream`, `/api/health`, upload boundaries, and function logs.
